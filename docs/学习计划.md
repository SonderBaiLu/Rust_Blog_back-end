## 二、三层理解（判断标准）

| 层级 | 特征 | 你的现状 |
| --- | --- | --- |
| **使用层** | 知道调什么 API，能跑通 | 大部分 API 在此层 |
| **机制层** | 知道内部发生了什么：编译器查什么、运行时调度什么、vtable 在哪 | 局部在此层 |
| **设计层** | 给陌生需求能独立决定分层/抽象/共享，并说得出每个选择的代价 | **目标，目前最弱** |

判断标准：使用层问「这是干嘛的」；机制层问「它为什么必须这样」；设计层问「我会不会这样，还有哪条路」。

一年目标：post 达到机制层，新模块达到设计层，最后能向陌生人 10 分钟讲透全链路。

## 六、训练方法（参考）

### 方法 1：记忆重构法（最有效，每周一次）

```
git stash                          # 藏起某模块完成代码
rm -rf src/modules/todo/           # 删掉
# 关文档、关 AI，凭记忆重建
cargo check                        # 让编译器当老师
git stash pop                      # 对比差异
```

重建后 `diff`，**每个写不出来的地方就是真正缺口**，记入 `docs/学习内容.md` 下周重测。

### 方法 2：预测先行法

每次 `cargo check` 前写下「我认为会报 N 个错，分别是……」，编译核对。猜错每条都是类型系统理解的漏洞。

### 方法 3：测试先行法（Q1 起强制）

写新业务逻辑前**先写一个必然失败的测试**，跑通前不许写实现。

### 方法 4：设计文档先行法

新模块先写 `docs/设计-xxx.md`（表结构/五层职责/权限矩阵/错误分支），代码和文档对不上以文档为准修代码。

### 方法 5：删层反推法

问「删掉 X 会怎样」，真的删，看编译器/运行时反应，再还原。每个实验「现象+原因」写进 `docs/踩坑记录.md`。

### 方法 6：教学复述法

每次学完一个点，写一段「教给一个会 Java/Python 的人」的说明，写不出来的地方 = 没学会。

### 方法 7：每周读一个源码文件

只读一个文件，回答：解决什么问题 / 关键设计 / 我代码里哪用到它。顺序：axum `extract.rs` → tokio task → sqlx 宏展开 → `thiserror` derive。

## 十、给 AI（包括我）的使用规则

固定协议，贴在每个新会话开头：

1. 「给我提示，不要给完整实现」——要方向/接口签名/测试用例设计，不要函数体。
2. 「先问我要不要测试先行」——让 AI 先陪你设计测试。
3. 「我写完后你只指出设计问题，不重写」——代码评审模式，不是代写模式。
4. 每学完一个点，让 AI 出 3 道「记忆重构题」自测。
5. 「我在走 B 分支」——告知分支 ID，AI 回答范围限定在该分支概念内。
6. 「全程中文讲解」——引用英文源码/文档时先翻译关键句成中文再展示原文。
