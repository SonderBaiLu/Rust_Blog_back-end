## 为什么每个文件都要写 struct 与 new？
**在 PgPostRepository 和 PostService 中出现的这套结构：**
~~~ rust
#[derive(Clone)]
pub struct PgPostRepository {
    pool: PgPool,
}

impl PgPostRepository {
    pub fn new(pool: PgPool) -> Self {
        Self { pool }
    }
}
and: 
#[derive(Clone)]
pub struct PostService {
    post_repo: Arc<dyn PostRepository>,
}

impl PostService {
    pub fn new(post_repo: Arc<dyn PostRepository>) -> Self {
        Self { post_repo }
    }
}
~~~
# 1. 用法
- 实例持有依赖：定义一个结构体，将其所依赖的底层资源（如数据库连接池 pool，或抽象持久层 post_repo）收敛为自身的私有成员字段
- 标准构造函数：通过关联函数 pub fn new(...) -> Self 强制要求调用者在创建该服务实例时，必须传入其所需要的全部依赖项。   
# 2. 设计理由（Design Rationale）
- 消除隐式全局可变状态（No Global State）：许多初学者习惯将数据库连接池定义为全局静态变量（如 static ref POOL: PgPool）。但在 Rust 的所有权与多线程模型下，全局变量不仅破坏并发安全、容易造成锁竞争，而且隐式跨模块共享会导致数据流向完全不可预测。将 pool 封装在实例内部，生命周期完全受控于调用链路。
- 参数传递的收敛（Ergonomics & Encapsulation）：如果不用结构体封装，那么 create_post、find_by_id、update_post 等每一个函数都必须在参数签名中显式携带 pool: &PgPool。随着业务层逻辑膨胀，每个函数都会拖着一长串底层基础设施参数。通过结构体，方法只需通过 &self.pool 隐式借用，对外保持干净的业务接口。
- 依赖倒置与可测试性（DIP & Testability）：
   看 PostService 的字段：post_repo: Arc<dyn PostRepository>。
   它持有的不是具体的 PgPostRepository，而是一个实现了 PostRepository 行为契约的特征对象（Trait Object）。   
  - 设计收益：业务层完全不关心数据到底存在 PostgreSQL、MySQL 还是内存中。   
  - 在编写自动化单元测试时，你可以直接写一个伪造的 MockPostRepository 塞给 PostService::new(mock_repo)，在完全不启动数据库的情况下对文章核心业务逻辑进行毫秒级测试。

# 3. 优缺点分析（Pros & Cons）
1. 优点：
   - 零隐式魔法：依赖关系透明清晰，在 main.rs 装配阶段即可一览整个系统的依赖图谱。   
   - 强编译期保障：漏传任何一个底层依赖，编译器会立即在 new() 调用处阻断，无法启动有缺陷的服务。
2. 缺点：
   - 相比于 Java Spring 的 @Autowired（隐式注解注入），Rust 的手动注入需要手写少量的结构体与 new 构造器模板代码（Boilerplate）。在 Rust 生态中，这是为了保证系统确定性与零运行时反射开销所采纳的行业标准实践。
