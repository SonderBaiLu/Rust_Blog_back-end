# 架构约定与避坑指南

> 本文记录这个 Rust Blog 项目在膨胀过程中总结出的架构约定，以及几个「现在还舒服、大了就难受」的坑。写新模块前先读一遍。

## 一、分层约定（写新模块的固定模板）

每个业务模块都按「按模块分」的结构内聚在 `src/modules/<模块名>/` 下，七件套各司其职：

| 文件 | 职责 | 说明 |
| --- | --- | --- |
| `entity.rs` | 数据库实体 | `FromRow`，直接映射表结构 |
| `dto.rs` | 请求 / 响应 / 查询契约 | 带 `validator` 校验，对外脱敏 |
| `repository.rs` | 持久层 trait | 定义数据访问契约，不关心具体数据库 |
| `postgres.rs` | Pg 实现 | `sqlx` 具体 SQL，实现上面那个 trait |
| `service.rs` | 业务逻辑 | 权限、状态流转、算法、审计日志 |
| `handler.rs` | HTTP 处理器 | 提取参数 → 校验 → 调 service → 返回 |
| `route.rs` | 路由挂载 | `xxx_routes() -> Router<AppState>` |

**跨模块的共享件留在 `src/` 根目录**，不要塞进某个模块里：

- `error.rs` — 统一 `AppError`
- `extractors/` — 鉴权提取器（`AuthUser`、`OptionalAuthUser`）
- `util/` — jwt / password / validator 等无状态工具
- `state.rs` — 全局 `AppState`
- `route/mod.rs` — 顶层路由聚合

### 新模块落地步骤（照着走一遍）

1. 建 `src/modules/<名字>/`，写 `mod.rs` + 七件套文件。
2. 在 `src/modules/mod.rs` 里 `pub mod <名字>;`。
3. 在 `state.rs` 的 `AppState` 加 `Arc<XxxService>`。
4. 在 `route/mod.rs` 加一行 `.nest("/api/v1/<前缀>", <名字>::route::<名字>_routes())`。
5. 跑 `cargo check`，确认无编译断裂。

## 二、铁律：Service 永远不依赖 Service

**规则：Service 只依赖 Repository（trait），绝不依赖另一个 Service。**

理由：一旦 Service 互相引用，模块一多就会出现循环依赖（A 依赖 B，B 又依赖 A），Rust 编译期直接卡死，而且循环依赖几乎无法靠「再加一层」优雅解决。

正确做法：谁要聚合多个模块的数据（比如统计面板 `DashboardService`），就**同时注入多个 repo**，而不是去依赖别人的 service：

```rust
pub struct DashboardService {
    post_repo: Arc<dyn PostRepository>,
    todo_repo: Arc<dyn TodoRepository>,
    habit_repo: Arc<dyn HabitRepository>,
}
```

Repository 是无状态的叶子节点，组合起来永远安全。现在的 `PostService` 只依赖 `post_repo`，`UserService` 只依赖 `user_repo`，是对的，保持这个方向。

## 三、保留 Repository trait，别为了省样板删掉它

有人会想：「我又不在测试里 mock，trait 是多余的样板」。别删。

这个 trait 是你未来三个能力的挂载点：

1. **单元测试**：写内存版 mock 实现 trait，service 就能脱离数据库测业务逻辑。
2. **离线同步**：未来接 App 时，同一套 trait 可以再实现一个 SQLite 版本。
3. **换数据库**：trait 把「用什么数据库」和「业务逻辑」解耦了。

## 四、别写「通用 CRUD 抽象」

**坑：** 想用泛型 + async trait 搞一个「一个 Repository 通吃所有实体」的抽象。

**代价：** async trait 的 object safety、关联类型、生命周期会把代码折腾到怀疑人生，最终得到的是一套比手写还难维护的宏/泛型魔法。

**正确做法：** 每个模块**显式但精简**地写自己的 trait 和实现。重复几行 CRUD 样板，好过一套玄学抽象。这是 Rust 生态里「显式优于魔法」的主流取舍。

## 五、依赖装配集中一处（AppState 膨胀问题）

模块多了之后，`AppState` 会变成 17+ 个字段，`main.rs` 里 30 多行手工装配。这不是错，但每加一个模块要改 `AppState`、`main.rs`、`state.rs` 三处。

**建议：** 把装配逻辑收敛成一个 `bootstrap(pool, config) -> AppState` 函数，让 `main.rs` 只做「读配置 → 建池 → 交给 builder → 拿回 state」。

```rust
// main.rs 最终形态
let state = bootstrap(pool, config).await?;
```

个人项目**不要**为此引入依赖注入框架 crate（`axum` 这种量的项目不值得），手写一个集中装配函数就够了。

## 六、离线同步的三条后端约定（接 App 前储备）

未来接移动端 / 桌面端时，后端必须提前长出的能力：

1. **客户端生成主键**：同步实体的 UUID 由客户端生成，服务器不生成，否则离线创建时没法确定 id。
2. **幂等 upsert + 增量拉取**：`POST /sync/upsert`（按 id 存在覆盖 / 不存在插入）、`GET /sync/changes?since=<updated_at>`（只拉变化）。
3. **软删除墓碑**：删除动作打 `deleted_at` 而不是物理删，否则删除同步不到其他端。

冲突策略：单人博客用「最后写入者胜（last-write-wins）」，以 `updated_at` 为准，不上 CRDT 这种重方案。

本地存储：SQLite 分「数据缓存表 + outbox 发件箱」，上传成功后删 outbox 行、保留数据缓存行（缓存的作用就是让离线还能用，别上传即删）。

## 七、其他零散约定

- **软删除统一**：所有表带 `deleted_at timestamptz`，查询时统一 `AND deleted_at IS NULL`。
- **时间字段统一**：`created_at` / `updated_at` 均 `timestamptz not null default now()`。
- **校验在 handler 层 Fail-Fast**：`req.validate()?` 放在 handler 第一步，非法输入不进 service。
- **日志用结构化字段**：`info!(post_id = %post.id, "文章创建成功")`，别把敏感信息（密码、token）打进日志。
- **对外脱敏**：实体（entity）和响应（DTO）分离，`From<Entity> for Dto` 里只挑安全字段。
- **错误不裸奔**：所有错误走 `AppError`，`IntoResponse` 统一映射成结构化 JSON，别在 handler 里 `unwrap()` / `expect()`。
